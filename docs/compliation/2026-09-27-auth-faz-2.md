## API ve güvenlik sözleşmesi

Tüm endpoint'ler kimliksiz ve rolesiz **public**; POST isteklerinde `XSRF-TOKEN` cookie değeri `X-XSRF-TOKEN` header'ında zorunludur. Başka public yol açılmadı. CORS yalnız `FRONTEND_URL` origin'ine izin verir. Auth token cookie'si ve login henüz yoktur.

| Yöntem / endpoint | İstek ve güvenli örnek | Başarı | Önemli hatalar |
| --- | --- | --- | --- |
| `GET /api/v1/auth/csrf` | Body yok | `200`, `XSRF-TOKEN` cookie ve `{"headerName":"X-XSRF-TOKEN"}` | Diğer yollar `403` |
| `POST /api/v1/auth/register` | `{"email":"member@example.test","nickname":"member_1","password":"örnek amaçlı 12+ karakter","confirmPassword":"örnek amaçlı 12+ karakter"}` | `202`, pending hesap ve mail gönderimi | `400` validation/eşleşmeme, `403` CSRF, `409` email/nickname çakışması, `429` IP sınırı, `503` mail yok |
| `POST /api/v1/auth/verify-email` | `{"email":"member@example.test","code":"000000"}` (temsili kod) | `204`, hesap ACTIVE | `400` hatalı/kullanılmış kod, `403` CSRF, `410` süresi dolmuş kod, `429` deneme sınırı |
| `POST /api/v1/auth/resend-verification` | `{"email":"member@example.test"}` | `202`, uygun pending hesaba yeni mail | `400` validation, `403` CSRF, `503` mail yok; bilinmeyen veya beklemedeki adres de `202` |

Yanıtlar hesap şifresi, kod, hash, SMTP secret veya iç hata ayrıntısı içermez. CSRF cookie'si JavaScript tarafından okunabilir; access/refresh tokenlar ileriki fazlarda ayrı HttpOnly cookie'lerde taşınacaktır. Kayıt hız sınırı uygulama belleğindedir, instance'lar arasında paylaşılmaz; client IP'si yalnız doğrudan bağlantı adresinden alınır, `X-Forwarded-For` güvenilmez. Reverse proxy veya çoklu instance topolojisi kesinleştiğinde bu sınır yeniden tasarlanmalıdır.

## Açık konular ve sonraki handoff

- Gerçek SMTP sağlayıcısına dış bağlantı bu testlerde yapılmadı; adapter sahte mail portu ile doğrulandı. Kullanıcının yerel secret ve SMTP ayarlarıyla uçtan uca mail teslimini kontrol etmesi gerekir.
- SMTP çağrısı DB transaction içinde yapılır. Mail sunucusu kabul ettikten sonra DB commit başarısız olursa e-posta gönderilmiş olup hesap geri alınabilir; bu nadir tutarlılık durumu üretim mail stratejisinde ele alınmalıdır.
- Onaylanan deny-all kuralı `/swagger-ui/index.html` ve `/v3/api-docs` yollarını da kapatır. Endpoint metadata anotasyonları eklendi; Swagger UI üzerinden canlı API denemesi bu fazda mümkün değildir. Swagger erişimi daha sonraki güvenlik kararı gerektirir.
- `EMAIL_VERIFICATION_HMAC_KEY` için gerçek Base64 kodlu en az 32 baytlık secret, `MAIL_ENABLED=true` ve mevcut SMTP ayarları kullanıcı tarafından yerel ortamda sağlanmalıdır. `FRONTEND_URL` eksik veya geçersizse backend güvenli şekilde başlamaz.
- Sonraki faz yalnız kullanıcı yönlendirmesiyle başlatılmalı; login/logout, JWT ve session yönetimi Faz 2 kapsamında uygulanmadı.

## Kullanıcı kontrolü

1. `.env.example` sözleşmesini inceleyin; yerel `.env` içinde `EMAIL_VERIFICATION_HMAC_KEY` değerini güvenli, rastgele Base64 32+ bayt key olarak sağlayın ve mevcut SMTP/MAIL ayarlarını kendi sağlayıcınıza göre yapılandırın. Secret'ı Git'e eklemeyin.
2. Docker Desktop açıkken Java 25 ile `backend` dizininde `mvn clean test` çalıştırın; tüm testlerin geçmesini bekleyin.
3. Çalışan uygulamada `GET /api/v1/auth/csrf` ile cookie alın. Cookie değerini `X-XSRF-TOKEN` header'ına koyarak register isteği gönderin; `202` ve doğrulama maili bekleyin. Header olmadan POST'un `403` olduğunu doğrulayın.
4. Maildeki kodla `POST /api/v1/auth/verify-email` çağırın; `204` ve hesabın `ACTIVE` durumunu bekleyin. Aynı kod tekrar kullanılamamalı. Swagger UI erişimi mevcut deny-all kararı gereği `403` olacaktır.
